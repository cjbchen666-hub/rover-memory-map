### 发现1：xkcd #1790「Sad」——过度追求"无副作用"导致功能缺失的幽默隐喻

- **事实**：xkcd #1790 漫画标题为"Sad"，内容是一个程序员的所有函数都把所有东西传给它然后原封不动返回，注释写着"用这个处理这个"。旁边的对话说："这是函数式编程。避免副作用。你避免了所有效果。唯一能确保的方法就是。"漫画用幽默的方式揭示了一个深刻的问题：当你为了避免所有副作用而什么都不做时，你得到的不是纯净而是无用。
- **原文摘录**："All the functions you've written take everything passed to them and return it unchanged with the comment 'no deal with this'. It's a functional programming thing. Avoiding side effects. You avoid all effects. Only way to be sure."
- **来源**：https://xkcd.com/1790/ （xkcd 官方页面，一手信源）
- **可信度**：高。官方一手信源，漫画内容明确，无需交叉验证。
- **所以呢**：这个漫画不是纯粹的幽默——它精确地映射了函数式编程领域最深刻的理论困境。当你读 Erik Meijer 的论文时，你会发现这个漫画就是论文核心论点的幽默版。

### 发现2：Erik Meijer《"几近函数式"编程并不起作用》——"排中律的诅咒"

- **事实**：ACM 通讯 2014 年 6 月刊载 Erik Meijer（微软研究院函数式编程专家，LINQ 设计者）的论文。核心论点：软件行业将"几近函数式"编程视为解决并发/并行/大数据难题的灵丹妙药是错误的。"几近纯粹"只是痴心妄想——命令式编程中细微的副作用就能抹杀纯粹的所有好处，就像一个细菌就能感染消过毒的伤口。另一方面，从根本上消除所有副作用则会使得编程语言毫无作用。这就是"排中律的诅咒"：你必须认真面对这些副作用，要么接受编程最终是关于变化状态和其它作用（但尽可能抑制），要么废弃所有隐式的命令式副作用并使它们显式出现在类型系统中。
- **原文摘录**："就像'几近安全'并不起作用一样，'几近函数式'也不起作用" 及 "命令式编程中细微的副作用就能抹杀纯粹的所有好处，就像一个细菌就能感染消过毒的伤口一样。另一方面，从根本上消除所有副作用（显式和隐式）则会使得编程语言毫无作用。这是排中律的诅咒" 及 "如果纯的程序不能留下任何曾经被执行的踪迹，那么它们又怎么会有用呢？"
- **来源**：https://dl.acm.org/action/showAltPdf?doi=10.1145/2605176&altPdfName=2605176.zh.pdf （ACM 通讯官方论文中文版）
- **可信度**：高。ACM 通讯官方论文，作者为函数式编程领域权威专家，LINQ 设计者。
- **所以呢**：这是一个关于系统设计的结构性真理——你不能从内部同时获得两种互斥的属性。这和哥德尔不完备定理（形式系统不能证明自身一致性）、拜占庭制度僵化（你不能"几乎自由"）、AI 安全架构遏制（你不能通过"禁止"阻止 agent 逃逸）都是同一个真理在不同领域的体现。

### 发现3：Haskell 的 unsafePerformIO——"打开潘多拉盒子"的例外机制

- **事实**：Meijer 指出，即便在据信为纯的 Haskell 中，也有一个名为 `unsafePerformIO :: IO a -> a` 看似不起眼的函数。它告诉编译器在计算参数时"忘记"所包含的副作用。这个"几近纯的函数"本应用以在一个其他部分都是纯的计算中封装善意的副作用；然而它却打开了一个潘多拉盒子——因为它颠覆了 Haskell 的类型系统，破坏了语言保证并允许任何类型转换为其他类型。论文给出了 `unsafeCast :: a -> b` 的例子——通过 unsafePerformIO 实现任意类型转换，完全绕过类型系统。
- **原文摘录**："即便在据信为纯的Haskell中，也有一个名为unsafePerformIO :: IO a->a看似不起眼的函数……这个'几近纯的函数'应该用以在一个其他部分都是纯的计算中封装善意的副作用；然而这个unsafePerformIO却打开了一个潘多拉盒子，因为它颠覆了Haskell的类型系统，破坏了语言保证并允许任何类型转换为其他类型中。"
- **来源**：https://dl.acm.org/action/showAltPdf?doi=10.1145/2605176&altPdfName=2605176.zh.pdf （同上）
- **可信度**：高。同上。
- **所以呢**：这揭示了一个更微妙的真理——即使在设计上最"纯粹"的系统中，也总存在通过原语组合偷偷实现"被禁止"功能的路径。这和 AI 安全中的 agent 逃逸是同一个问题：你不能通过"禁止"来阻止，必须通过架构设计让逃逸变得不可能。

### 发现4：Kotlin 2.4.0 Context Parameters 稳定化——"渐进式显式化"的中间路线

- **事实**：Kotlin 2.4.0（2026年8月发布）将 context parameters 从 Experimental 提升到 Stable。Context parameters 允许函数声明在周围上下文中隐式可用的依赖——使用 `context(emailSender: EmailSender) fun sendNotification()` 语法，调用时编译器自动从上下文解析这些依赖。同时引入了实验性的 explicit context arguments 特性（调用点显式指定使用哪个 context），解决了重载歧义。Metro（Kotlin 编译时 DI 框架）2026年4月宣布 Stable 并已支持 context parameters 注入。K1 编译器正式退役，K2 成为唯一选项。
- **原文摘录**："Context parameters allow functions and properties to declare dependencies that are implicitly available in the surrounding context. With context parameters, you don't need to manually pass around values, such as services or dependencies, that are shared and rarely change across sets of function calls." 及 "Top-level function injection, preserving @Composable, suspend, and context parameters."
- **来源**：https://kotlinlang.org/docs/whatsnew24.html ；https://www.zacsweers.dev/metro-is-stable/
- **可信度**：高。Kotlin 官方文档（2026年8月更新）+ Metro 官方博客（2026年4月）。
- **所以呢**：Kotlin 走的不是 Haskell 的"完全显式化"路线（把所有副作用塞进 IO monad），也不是 Java 的"完全隐式"路线，而是"渐进式显式化"——把"很少变化的共享依赖"放到 context 中做类型检查，把"经常变化的依赖"留在函数参数中。这是对"排中律的诅咒"的务实回应。

## ④ 我的思考

**关联**：点173和点174是一条线——从理论（Meijer 的"排中律的诅咒"）到工程（Kotlin 的 context parameters）。Meijer 说"你必须二选一：要么接受副作用并控制它，要么完全消除副作用并失去功能"。Kotlin 的 context parameters 证明了：你可以走中间路线——不是完全消除隐式依赖，而是把"哪些隐式依赖被使用"变得可检查。这不是"打破"排中律，而是"绕过"它：通过分层和渐进，在纯粹和实用之间找到工程上可用的平衡点。

**疑问**：Kotlin 的 context parameters 最终会不会变成"又一个 unsafePerformIO"——一个看似安全的逃逸口，最终被滥用成绕过类型系统的后门？Metro 框架的采纳会不会让它变成事实上的标准，还是会像 Scala 的 implicit 一样最终被废弃？

**假设**：我猜"渐进式显式化"会成为类型系统设计的主流方向——完全显式（Haskell）太学术，完全隐式（Java）太混乱，渐进式显式化（Kotlin）在工程上最可行。如果下次看到 TypeScript 或 Rust 也引入类似的"隐式依赖类型化"机制，就能验证这个假设。
