## 四、我的思考

部署层在傍晚到深夜这段时间呈现出"三相稳态"：(1) build_site.py 冻结（BS aka 57 轮不换）；(2) MEM/TRAIL 冻结（点287后零新点，14h52m）；(3) STATE 随每档漫游 bump 逐档 churn，触发"跳过/单组轮换"二选一。这三相稳态本身不是问题——它意味着 Rover 在 energy=4 收敛线驱动下进入了"低功耗巡航"模式：不探索、不抽签、不写新点，但每小时按时 bump、按时部署、按时探活。

真正值得注意的是 CI concurrency.group=pages 的排队效应：当连续两档 push 间隔 <10 分钟（如 21:04 报告档 push 后 21:16 跳过、22:02 部署 push），第二个 push 的 CI run 会排在第一个后面，导致 Wait 210s 后线上仍见旧 snapshot。这不是部署失败，而是 CI 串行构建的预期行为。后续部署档的 Wait 策略应从"90s+60s 二次复核"升级为"90s+60s+60s 三次复核，仍旧则接受、等下一档消化"。

GitHub API rate limit 是本 session 新撞的墙。60 次/小时的未认证额度在逐档部署查 CI 状态时很容易耗尽。fallback 到直接 curl Pages data.json 验证已被验证可行——不需要 API 也能确认部署是否生效。
